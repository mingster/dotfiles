# Daily program kickoff

The coordinator runs the standing program from here each day at 19:00 Taiwan time, when the `daily-program-1900` Orca automation wakes it. The wake says whether staging is behind `origin/main`. The run time, the digest query and its read only database URL are in the project's `docs/agents/team-facts.md` (Daily run). Spawn each step to the role that owns it through Orca orchestration under `.agents/skills/orca-adapter/ORCA-ADAPTER.md`; do not do their work. This is a coordinator schedule, not a gate: fleet-watch's issue scan starts builders and its babysit pass starts verifiers all day, the PR owner merges its own PR with `ship.sh`, and nothing in this run waits for them or they for it (`team.md`, No bottleneck and Publication). Follow `.claude/agents/elon.md` for anything not said here.

Take yesterday's state from PRs, issues and the task list, never from chat memory. The program gets the team working; it is more than a report. Do the steps in order. Message the user at the end only when a step needs a user decision.

1. **Digest.** Run the project's digest query. Hand each abnormal line to its owner: tickets and contact messages to support-csm, failed charges and ledger anomalies to secops-finops, cron, backups, hosts and errors to qa-sdet, signup drops or cancellation rises to sales-marketing. Anything broken becomes an `incident` issue (or a comment on the open one) before step 2. **Support queue:** take every open ticket, contact message and support email through the support ticket rule in `.claude/agents/elon.md` the same day: fix if needed, support-csm drafts the reply in the customer's language, the coordinator sends the user the ticket, what was done and the draft. Nothing is sent before he approves.
2. **Triage.** architect-pm runs the `triage` skill (`~/.agents/skills/triage/SKILL.md`, the coordinator as maintainer, an agent brief on each `ready-for-agent` issue) on each `needs-triage` issue and replaces the label: `ready-for-agent` (enough detail, not gated, contradicts nothing), `ready-for-human` (only an owner pause in `team.md`, or a step only the owner can take with his own hands or accounts; comment the question with a recommendation), `needs-info` (comment what is missing). A product change needs an intent: architect-pm drafts it and the issue is `ready-for-agent`; only money rules and prices wait on the owner (`team.md`, Owner pauses). A bug without a P label goes to architect-pm to rate.
3. **Issue budget.** Apply the Issue budget in `team.md`. Close duplicates (`Duplicate of #N`), issues a merged PR fixed, and issues about code that no longer exists, each as not planned with a one line reason. Fix label drift: `ready-for-agent` on an issue whose body says blocked, `blocked` with nothing named. Report an **Issues** line under **Now**: opened, closed and net for 24 hours, and the open count.
4. **Open team PRs.** Read each open team PR's state for the report; start nothing for it by hand. fleet-watch starts the verifier (never hand-dispatch one, `elon-dispatch.md`) and its rework; the PR owner rebases, takes its fix rounds (2 rounds, then the coordinator decides or escalates), merges `main` in on a conflict with `resolving-merge-conflicts` (never a force push) and merges with `ship.sh` on a passing Verdict. Ask secops-finops for a review when the diff touches auth, tenancy, rate limits or money. A PR stuck with nobody acting is a fleet-watch bug: file it.
5. **Pipeline.** When the wake says staging is behind `origin/main`, release-manager runs `/deploy local` on `origin/main`, then `/deploy staging` if it passed, then qa-sdet runs the pstack `swarm` live lanes on staging (`.agents/skills/orca-adapter/playbooks/swarm.md`), with the journey walk brief in the project's `docs/agents/deploy-facts.md` when it has one. When staging equals main, skip the deploys and the live lanes. When staging has passed smoke and is ahead of production: while production holds only test data, release-manager runs the Playground regression and deploys production when it passes (deploy skill, Test data only); once a real store is live, the coordinator asks the user: `Ready for owner to approve production: <sha>, <N> PRs. Owner runs: bin/owner-approve.sh promote <sha>`, and release-manager deploys once he has run it. List it on the **Deployed** line. A failed stage goes in the report with its error and the issue opened for it.
6. **New work.** fleet-watch's issue scan starts a builder on a `ready-for-agent` issue with no open PR whenever a seat is free, up to the WIP cap in `team.md`, with no hold behind open PRs. Order: `hotfix`, `incident`, titles starting `Security:`, `bug` by P label, then the rest, oldest first. Report how many started; an issue that is ready with a free seat and did not start is a fleet-watch bug: file it.
7. **Mondays.** Also ask support-csm for the satisfaction and common pain points report and sales-marketing for the combined commercial and growth report; put the top findings under **Now**.
8. **Report.** One message in the three part shape, with **Merged** (each PR merged since the last run, number and title), **Deployed** (the commit now on local, staging, production) and the **Issues** line.

Run `/team-audit` only when the user says "team-audit".

Never in the daily run: deploy or roll back production once a real store is live without the owner's `bin/owner-approve.sh`, or before that without a passing Playground regression, write to production data, message a customer or store, close a ticket, or close an issue as completed without a merged PR (duplicate, already fixed or backlog closures under step 3 are allowed). No personal data in the report.

## Reporting

Send the completed report to the coordinator. On Mondays, sales-marketing's combined report adds qualified pipeline, wins and losses, paid conversions, revenue evidence, experiment results and the next three growth bets. SecOps reports independent material risk to the coordinator. Keep critical or suppressed-concern escalation open.
