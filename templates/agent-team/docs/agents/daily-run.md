# Daily run (`/elon daily run`)

Run by Elon (the main session) and loaded only for `/elon daily run`. The run time, the digest query and its read-only database URL are in the project's `docs/agents/team-facts.md` (Daily run). Dispatch each step to the role that owns it with Orca orchestration; do not do their work. Follow `.claude/agents/elon.md` for anything not said here.

Start each run in a new session, never `--continue` or `--resume`: yesterday's context is in PRs, issues and the task list. The run gets the team working; it is more than a report. Do the steps in order. Message the owner at the end only when a step needs his decision.

1. **Digest.** Run the project's digest query. Hand each abnormal line to its owner: tickets and contact messages to support-csm, failed charges and ledger anomalies to secops-finops, cron, backups, hosts and errors to qa-sdet, signup drops or cancellation rises to sales-marketing. Anything broken becomes an `incident` issue (or a comment on the open one) before step 2. **Support queue:** take every open ticket, contact message and support email through the support ticket rule in `.claude/agents/elon.md` the same day: fix if needed, support-csm drafts the reply in the customer's language, Elon sends the owner the ticket, what was done and the draft. Nothing is sent before he approves.
2. **Triage.** architect-pm runs the `triage` skill (`~/.agents/skills/triage/SKILL.md`, Elon as maintainer, an agent brief on each `ready-for-agent` issue) on each `needs-triage` issue and replaces the label: `ready-for-agent` (enough detail, not gated, contradicts nothing), `ready-for-human` (owner decision; comment the question with a recommendation), `needs-info` (comment what is missing). A product change needs an intent: architect-pm drafts it and the issue is `ready-for-human`. A bug without a P label goes to architect-pm to rate.
3. **Issue budget.** Apply the Issue budget in `team.md`. Close duplicates (`Duplicate of #N`), issues a merged PR fixed, and issues about code that no longer exists, each as not planned with a one line reason. Fix label drift: `ready-for-agent` on an issue whose body says blocked, `blocked` with nothing named. Report an **Issues** line under **Now**: opened, closed and net for 24 hours, and the open count.
4. **Open team PRs.** No review yet: spawn qa-sdet, plus secops-finops when the diff touches auth, tenancy, rate limits or money. Blocking comments or failing checks: spawn fullstack-dev on that branch (2 rounds, then Elon decides or escalates). Merge conflict with `main`: fullstack-dev merges `main` in with `resolving-merge-conflicts`, never force pushes. No blocking comments and green checks: merge.
5. **Pipeline.** After merges, release-manager runs `/deploy local` on `origin/main`, then `/deploy staging` if it passed. When staging has passed smoke and is ahead of production, Elon asks the owner: `Ready for owner to approve production: <sha>, <N> PRs. Owner runs: bin/owner-approve.sh promote <sha>`. release-manager deploys once he has run it; list it on the **Deployed** line. A failed stage goes in the report with its error and the issue opened for it.
6. **New work.** While fewer than 10 team PRs are open, pick up to 3 `ready-for-agent` issues with no open PR. Order: `hotfix`, `incident`, titles starting `Security:`, `bug` by P label, then the rest, oldest first. At 10 or more open, start nothing new and say so.
7. **Mondays.** Also ask support-csm for the satisfaction and common pain points report and sales-marketing for the combined commercial and growth report; put the top findings under **Now**.
8. **Report.** One message in the three part shape, with **Merged** (each PR merged since the last run, number and title), **Deployed** (the commit now on local, staging, production) and the **Issues** line.

After each staging deploy, dispatch the journey walk with the brief in the project's `docs/agents/deploy-facts.md` (Staging review, Journey walk brief), when it has one. Run `/team-audit` only when the owner says "team-audit".

Never in the daily run: deploy production without the owner's `bin/owner-approve.sh`, roll back, write to production data, message a customer or store, close a ticket, or close an issue as completed without a merged PR (duplicate, already fixed or backlog closures under step 3 are allowed). No personal data in the report.

## Reporting

Send the completed report to Elon. On Mondays, sales-marketing's combined report adds qualified pipeline, wins and losses, paid conversions, revenue evidence, experiment results and the next three growth bets. SecOps reports independent material risk to Elon. Keep critical or suppressed-concern escalation open.
