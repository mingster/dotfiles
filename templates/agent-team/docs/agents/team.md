# Agent team

{{PROJECT_NAME}} is operated by its human user and a team of AI agents: the coordinator (CEO) and specialist roles. The user talks to the coordinator, who delegates work and contacts the user only for a decision the coordinator cannot make. Role files live in `.claude/agents/`; this file lives once in `~/dotfiles/templates/agent-team/docs/agents/team.md`, and project differences go in `docs/agents/team-facts.md` only (deploy facts in `docs/agents/deploy-facts.md`).

Every role works through pstack `poteto-mode` and `.agents/skills/orca-adapter/ORCA-ADAPTER.md`. This file holds only facts and the rule table, never a pstack principle or playbook. GitHub issues and PRs are the state of record.

| Role | File | Primary output |
| --- | --- | --- |
| The coordinator (CEO) | `elon.md` | Priorities, user contact, dispatch |
| architect-pm | `architect-pm.md` | One document per feature (intent, spec and units), issue triage, weekly list |
| fullstack-dev | `fullstack-dev.md` | Isolated branch with its own tests. Cursor `grok-4.7-xhigh`; Claude only when that quota is out |
| qa-sdet | `qa-sdet.md` | Verifier Verdict (`script/post-verdict.sh`), Playwright runs, weekly swarm live lanes |
| secops-finops | `secops-finops.md` | Money and auth PR reviews, weekly reconciliation |
| support-csm | `support-csm.md` | Ticket triage, reply drafts and recurring pain points |
| release-manager | `release-manager.md` | Staging in the daily program (`daily-run.md`), production after the Playground regression, or on the owner's go once a real store is live, rollback plan (a production rollback is a production deploy) |
| sales-marketing | `sales-marketing.md` | Positioning, acquisition plans, growth experiments, weekly numbers |

| Severity | Meaning | Action |
| --- | --- | --- |
| P0 | Critical security, financial or production outage | Hotfix immediately; involve SecOps |
| P1 | Core workflow broken without a workaround | Hotfix immediately |
| P2 | Issue with a workaround or limited impact | Normal queue |
| P3 | Cosmetic or wording issue | Normal queue |

Usage gate by coordinator host: `usage-gate-hook.py` gates every worker start from Claude Code (`.claude/settings.json`), Cursor (`~/.cursor/hooks.json`) and Antigravity (`~/.gemini/config/hooks.json`). The Cursor and Antigravity entries come from `~/dotfiles/script/setup-cursor.sh` and `setup-antigravity.sh`; a coordinator that starts workers from either IDE first confirms its entry is installed, and otherwise runs in Claude Code.

Before judging engineering reviews or tests, the coordinator reads `~/dotfiles/templates/agent-team/docs/agents/engineering-integration.md`. Release failure classification follows `.agents/skills/deploy/SKILL.md`, Test noise.

## Rule table

Each rule names what enforces it. "none" means only the agent's reading holds it; those rows are follow up work. Before adding a rule, step or check, apply The Algorithm (row below).

| Rule | Enforcer |
| --- | --- |
| **No bottleneck (owner 2026-11-13, #986):** "Elon or human cannot be bottleneck." Nothing waits on the coordinator: each step (labeling, dispatch, verifier, rebase, merge, worker release) runs automatically or by the role that owns it, with a written default when a person does not answer. Only the owner pauses below wait on the owner, and only at their merge, send or deploy step; they hold nothing else, and the coordinator sends the owner one batched list, not one ping per item. A worker never ends its turn waiting for an answer: it asks, names its default, and proceeds on it. A step that still needs the coordinator is a bug: file it. | none (code gaps: #1016, #1017) |
| **Owner pauses (owner, coordinator chat 2026-11-13):** exactly these wait on the owner, and "owner-reserved" means this list: money rules and prices; spending and contracts (paid overage, new paid services, budget, legal); customer messages (each draft); irreversible data deletion; production deploy once a real store is live; and one look at a new feature or page (screen or screenshot) before it reaches production, which the owner can stop. Role file and hook changes, weekly update PRs and builds of new features need no owner approval; a change that loosens a safety limit (production access, data deletion, secrets, payment) still does. | none |
| **The Algorithm:** apply `principle-the-algorithm` before any new rule, step or check. The PR names the requirement it questioned and what it deleted. | none |
| **User decisions:** pricing, legal, production and irreversible data are never declined by the team, only pushed back to the user with evidence. | none |
| **Plan approval (owner, coordinator chat 2026-11-13):** the user approves prices and money rules before build. New features and pages build without approval and get the owner's look before production. The coordinator decides the rest and records it on the issue. | none |
| **Pre-build grill gate (user 2026-11-06):** a multi role grill runs only for money (payments, billing, refunds, ledger, credits, pricing or entitlements) with secops-finops, architect-pm and the coordinator, and for new UI pages with sales-marketing and the coordinator. The coordinator approves grill results, except money rules and prices: there the build runs up to a green PR with a Verdict while the owner reviews the grill result, and only the merge waits (owner 2026-11-13, #986). A new page needs no approval before build; the owner's look comes before production (Owner pauses). | `.claude/hooks/guard-bash.py` (grill check on build worker starts) |
| **Role changes (owner, coordinator chat 2026-11-13):** a change to a role definition (`.claude/agents/`, other provider role files, canonical role templates) or a hook merges on a passing non-author Verdict with the coordinator's approval, and the coordinator lists these changes to the owner weekly. A change that loosens a safety limit (production access, data deletion, secrets, payment) needs the owner's explicit approval of the concrete diff; silence, QA PASS or Checks PASS is not approval. Each commit carries `Owner-approved: <approver> <date> (<where approved>)`. | `script/team-audit.sh` (flags commits from 2026-11-03 without the trailer), `script/ship.sh` |
| **Gated actions:** only the user approves messages to customers, partners or the public, closing customer tickets, refunds, credits, discounts, coupons, subscription changes, production data writes, direct production server access, production deploys and rollbacks once a real store is live (before that, either runs after the Playground regression passes), spending, force pushes, and accepting or rejecting an intent or spec on money rules or prices. | `.claude/hooks/guard-bash.py` (production push, force push, approval scope); none for the rest |
| **Orca dispatch:** dispatch only through Orca orchestration; the in flight count comes from the fleet caps and the usage gate. | `script/usage-gate.py`, `usage-gate-hook.py` |
| **Allowed scripts:** "call no scripts" bans ad hoc coordination scripts only. The usage gate, `heavy-gate.sh`, `ship.sh` and worker-watch stay. | `.claude/hooks/guard-bash.py` (un-gated heavy jobs) |
| **Publication (owner 2026-11-13, #986):** one owner per PR. The PR owner writes the branch and carries it to merge, including rebases and fix rounds, and lands it with `ship.sh` on a PASS Verdict at the current head from a verifier that is not its author. The coordinator does not merge by hand. fleet-watch auto-ship is the backstop for a verified PR whose owner has settled (#1016). | `script/ship.sh`, `script/team-audit.sh` (merge wording) |
| **Stall detection:** stays on worker-watch. | `~/dotfiles/.agents/skills/orca-team/worker-watch.sh` |
| **Child ledger:** the coordinator keeps a ledger row for every child (task ID, dispatch ID, terminal, worktree, branch, full head SHA, state, next actor, evidence path). | none |
| **Background waits:** every wait runs in the background with a timeout; in Claude Code as its own Bash call with `run_in_background: true`, never a shell `&`. | `.claude/hooks/guard-bash.py` (trailing `&` on `check --wait`) |
| **No run-use for workers:** workers and child coordinators never run `orca orchestration run-use`. The coordinator rebinds with `run-use --id <run>` after a restart. | none |
| **Release settled workers:** every settled child, including FAILED, gets `worker-release` and its ended panes closed. | `script/wrap-up.sh` |
| **Redesign:** a PR whose Verdict or Review failed twice gets no third patch. It gets the `needs-redesign` label, and the coordinator closes it with the lesson and dispatches a fresh worker on a new brief. The owner is asked only if the redesign also dead ends. | `script/pr-review.sh` |
| **Extra Strong review (user 2026-10-31):** extra Strong cross review only for money transactions, or when the coordinator or the user asks for it on that issue. | `script/pr-review.sh` (money paths) |
| **Merge host (2026-11-09):** `ship.sh` runs on the coordinator's host. A PR owner running on another host leaves its verified PR to fleet-watch auto-ship there. | `script/worker-startup.sh` (refuses `--on` for a brief titled `release-manager: merge`) |
| **Board status (user 2026-11-12):** every worker's Finish runs `orca worktree set --worktree active --workspace-status in-review` before `worker_done`. A release with no PR sets `completed`, and `ship.sh` sets it after a merge. | `script/brief-lint.sh` (Finish must say so), `.agents/skills/orca-team/worker-pane-close.sh`, `script/ship.sh` |
| **Database head checks (2026-11-09):** a head check with a database step runs on the database host, never a host with no Postgres. `createdb: command not found` is a host fault, not a pass and not done. | `script/head-checks.sh` (sends the step to the `head_checks_remote` host when Postgres is absent here, otherwise FAIL as a host fault) |
| **Antigravity login (2026-11-09):** after starting an Antigravity worker, read its screen. A login prompt still shows ready and live. | none |
| **Reach a remote worker (2026-11-09):** send to a worker on another host with `orca terminal send --environment <env>`, never `orchestration send`. | none |
| **Acceptance checklist (owner 2026-11-13, #986):** a brief's Acceptance is a `- [ ]` list. The builder copies it into the PR body and writes the proof beside each box: a file path, a command with its output line, or `n/a: <why>`. A behaviour item is proved on the real artifact (live run or screen), not only a unit test, and a test the builder adds or tightens runs across every variant it covers (locales, views). A box without proof is not done. | `script/brief-lint.sh` (Acceptance present); none for the proofs |
| **Verdict:** a PASS Verdict includes `Command: <exact test command run>`. The verifier is a different model family from the builder (Claude, GPT, Grok, Gemini; sonnet and opus are one family). It walks the PR's Acceptance list item by item and FAILs on each unproved item, naming it, so the rework brief is that item. The Verdict judges the brief, not taste: extras become a follow up issue. A rework fixes only the named items. Never edit or minimize a Verdict; post a new one. | `script/post-verdict.sh`, `script/ship.sh` |
| **Verdict carry (user 2026-10-23):** a PASS survives a rebase when the `git patch-id --stable` of `merge-base(origin/main, head)..head` matches the Verdict head. | `script/ship.sh` (`verdict_carry`) |
| **Wording only after a Verdict (owner 2026-11-13, #940):** when the Verdict head differs from the head, `ship.sh` merges on green checks with no new Verdict if every file changed between them is `.md` under `docs/` or `changelog.d/` or at the top level, the diff adds no code fence, and no changed path is protected (`script/lib/protected-paths.sh`). Anything else keeps the patch-id rule. | `script/ship.sh` (`wording_only_carry`) |
| **Head checks (user 2026-10-27):** proving commands include every `.agents/head-checks.conf` command for the changed files, with `shellcheck --severity=error` on each changed `.sh`, once, at the head. | `script/head-checks.sh` |
| **WIP cap (user 2026-10-23):** at most 6 open PRs per project; at 6, start no new feature unit. Test fix, hotfix and user UI look PRs are exempt. This is the only limit on starts besides seats and the usage gate: a free seat and a `ready-for-agent` issue mean start now, with no hold for open PRs to merge first (owner 2026-11-13, #986). Owner-reserved PRs waiting on the owner count toward the cap. | `script/fleet-watch.py` (issue scan starts on a free seat) |
| **One PR per fix batch (user 2026-10-23):** fixes from one regression run or failing area go in one PR. | none |
| **Copy at the spec (user 2026-10-23):** the spec and each unit carry the exact new strings in tw, en and jp; they are reviewed with the spec, and the owner sees them in the look before production (Owner pauses). | none |
| **Native copy (user 2026-10-21):** `en` is fluent American English and `jp` natural Japanese, never word for word from `tw`. A menu or button name quotes the real label in that locale's file. | none |
| **New UI page (user 2026-10-26):** a new page builds without approval; the owner's look before production uses phone screenshots of the design or prototype (Owner pauses). Screenshots go in `~/.claude/state/screenshots/<repo>/<issue>/`. | none |
| **Straight to staging (user 2026-10-23):** release-manager promotes trunk to staging after merges. Production needs the user's go per release once a real store is live (Owner pauses). Japanese homepage copy needs a native reader before launch. | none |
| **Heavy jobs (user 2026-11-08):** Playwright and production builds run through `~/dotfiles/script/heavy-gate.sh --weight 2`; a long regression sets `HEAVY_GATE_CLASS=long`; full `tsc` uses `--measure`. Only the coordinator runs `hw-probe.sh --calibrate`. | `.claude/hooks/guard-bash.py`, `script/heavy-gate.sh` |
| **Strikes:** follow the project's token budget and strike rule in `AGENTS.md`. | `.claude/hooks/strikes.py` |
| **Zero secrets:** never print env files, secrets or keys to output or markdown; never open a secret file with a printing command. | `.claude/hooks/guard-bash.py` (secret readers, `.env` copies) |

| **One unit, one session:** start a fresh session for a new unit; keep `active_run.md` current for long tasks. | none |

If one is already being built, file the new issue with a GitHub blocked-by link to it; issue scan skips blocked issues, so the second starts on a fresh main after the first merges, with no rebase. | `script/fleet-watch.py` (`issue_scan_blocked`) |

Never label an issue a worker is already doing. A small PR finding is fixed in that PR, otherwise one follow up issue per PR. | none |
