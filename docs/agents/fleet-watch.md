# Fleet watchdog

Run `python3 script/fleet-watch.py --config <private-json> --state <private-state>` once each minute from a supervisor independent of the coordinator's inbox waiter. Configure `runs` with each run's `id`, `terminal` (coordinator handle) and `waiter_pattern` (a process pattern unique to that run); host caps and load ceilings are not in this config: they come from `fleet-config.json` (default `~/.claude/state/fleet-config.json`, or the `fleet_config` key), keyed by the host IDs returned by worker-list. A host not listed keeps the cap of 4. When that file is missing or unreadable, `--admit` refuses and one notice goes out until it reads again. Optional `leads` lists each lead's `name` and `terminal`; a lead whose `orca terminal show` fails gets one alert, rearmed when it answers again. Keep handles and machine names in the private config, never in this repository.

A waiter absent across ten minutes of observations with unread deliveries gets one alert, then rearms when the waiter returns or the inbox clears. The first pass records existing failed dispatches without alerting. After that, each new failed dispatch gets one alert. Every nonfinal dispatch, including children, counts toward host capacity. The watchdog only alerts; the coordinator follows Orca recovery before stopping or retrying anything. A CLI failure preserves state and fails the pass so the supervisor can report it. Without an independent minute scheduler this is an unactivated guard, not liveness coverage.

Optional `coordinator_watch` (`state_dir`, `offline_minutes` defaulting to 10, `alert_command`) belongs in the config of a backup host only, because a coordinator cannot report its own death. Each pass runs `git -C <state_dir> fetch -q origin` (ten second limit), then `git -C <state_dir> show origin/main:coordinator.conf`, and reads `coordinator <name>` from that text; on any git failure it falls back to `<state_dir>/coordinator.conf`. With no such line, or when this host is the named coordinator, it does nothing. Otherwise each pass runs `ssh -o BatchMode=yes -o ConnectTimeout=6 <name> true` with a ten second limit; a failed fetch alone does not count as the coordinator being offline. After `offline_minutes` of ssh failures it sends one alert, `coordinator <name> offline for <n> minutes; failover is manual, ask the owner`, by running `alert_command` with the text as its last argument (the private config picks the channel) and adding it to the normal notices even when `alert_command` fails, so configured runs and the log still see the line; a failed `alert_command` leaves `alerted` false and is retried on the next pass. When the coordinator answers again the state clears and one `coordinator <name> back` line goes out if an alert had been sent. A changed coordinator name resets the timer. This check runs first, before any Orca call, and saves its state at once. With `runs` empty it skips every Orca call, so a host without Orca passes cleanly. It only alerts: it starts nothing and fails over nothing.

Nothing is typed into a terminal. Notices queue in the state file and go to each run terminal as one `orchestration send`, at most every 600 seconds, oldest first with duplicates merged. A `lead pane gone`, `host cap exceeded`, `failed dispatch` or `inbox waiter absent` notice goes at once as a message, with whatever is queued. A Verdict notice goes at once to the lead named by the owner record of its `author=` dispatch, and to the digest when there is no record. A failed send keeps the queue and retries on the next pass; an entry that still fails after 20 passes is dropped with a line on stderr. The send time and queue are saved in the state file, so a restart neither floods nor drops.

`script/coordinator-drain.sh` replaces the bare `orchestration check` in the coordinator's waiter. The waiter command becomes `FLEET_WATCH_CONFIG=<private-json> script/coordinator-drain.sh --run <run> --wait`, with the same `<private-json>` that fleet-watch gets as `--config`. It takes the same arguments, prints the same JSON, and leaves out "Worker stopped without reporting" for a lead terminal (from `leads`, read from `FLEET_WATCH_CONFIG`; the default `~/.config/fleet-watch/config.json` has no `leads` key on a coordinator, so without the variable nothing is dropped and each check says so on stderr). Each dropped stop appends the lead's handle to `COORDINATOR_DRAIN_STATE` (default `~/.claude/state/coordinator-drain.log`), and fleet-watch turns that log into one digest line with a count per lead. It logs the number dropped on stderr. A worker's stop always passes.
