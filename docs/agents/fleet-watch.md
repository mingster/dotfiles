# Fleet watchdog

Run `python3 script/fleet-watch.py --config <private-json> --state <private-state>` once each minute from a supervisor independent of the coordinator's inbox waiter. Configure `runs` with each run's `id`, `terminal` (coordinator handle) and `waiter_pattern` (a process pattern unique to that run); configure `host_caps` using the host IDs returned by worker-list. Optional `leads` lists each lead's `name` and `terminal`; a lead whose `orca terminal show` fails gets one alert, rearmed when it answers again. Keep handles and machine names in the private config, never in this repository.

Each pass appends one summary line to `~/.orca/logs/fleet-watch.log` (pass duration, backup stamp age when `backup.stamp` is set, and any worker-stall actions). It never logs terminal screen content.

Optional `worker_stall`: set `label_repo` to a GitHub repo where stalled-worker issues and labels are applied (`needs-elon` by default). When a live worker's terminal has had no `lastOutputAt` progress for 30 minutes, the pass runs `worker-stop` once then `worker-start --retry-of <dispatch>`; if progress is still missing after the label cooldown, it adds the `needs-elon` label to the PR whose number appears on the worker row, or opens a fixed-title issue when there is no PR number.

A waiter absent across ten minutes of observations with unread deliveries gets one terminal wake, then rearms when the waiter returns or the inbox clears. The first pass records existing failed dispatches without alerting. After that, each new failed dispatch gets one alert. Every nonfinal dispatch, including children, counts toward host capacity. The watchdog only alerts; the coordinator follows Orca recovery before stopping or retrying anything. A CLI failure preserves state and fails the pass so the supervisor can report it. Without an independent minute scheduler this is an unactivated guard, not liveness coverage.

Optional `coordinator_watch` (`state_dir`, `offline_minutes` defaulting to 10, `alert_command`) belongs in the config of a backup host only, because a coordinator cannot report its own death. Each pass runs `git -C <state_dir> fetch -q origin` (ten second limit), then `git -C <state_dir> show origin/main:coordinator.conf`, and reads `coordinator <name>` from that text; on any git failure it falls back to `<state_dir>/coordinator.conf`. With no such line, or when this host is the named coordinator, it does nothing. Otherwise each pass runs `ssh -o BatchMode=yes -o ConnectTimeout=6 <name> true` with a ten second limit; a failed fetch alone does not count as the coordinator being offline. After `offline_minutes` of ssh failures it sends one alert, `coordinator <name> offline for <n> minutes; failover is manual, ask the owner`, by running `alert_command` with the text as its last argument (the private config picks the channel) and adding it to the normal notices even when `alert_command` fails, so configured runs and the log still see the line; a failed `alert_command` leaves `alerted` false and is retried on the next pass. When the coordinator answers again the state clears and one `coordinator <name> back` line goes out if an alert had been sent. A changed coordinator name resets the timer. This check runs first, before any Orca call, and saves its state at once. With `runs` empty it skips every Orca call, so a host without Orca passes cleanly. It only alerts: it starts nothing and fails over nothing.

Optional `backup` with `stamp` (mtime of the last successful private-repo sync) and `issue_repo`: when the stamp is over 30 minutes old the pass opens one issue with the fixed title `agent-state backup has not pushed for 30 minutes` (same as T3). The log line includes `backup_age_s=…` and adds `backup_stale` when the age exceeds 10 minutes so a blocked sync is visible between issue thresholds.
