# Fleet watchdog

Run `python3 script/fleet-watch.py --config <private-json> --state <private-state>` once each minute from a supervisor independent of the coordinator's inbox waiter. Configure `runs` with each run's `id`, `terminal` (coordinator handle) and `waiter_pattern` (a process pattern unique to that run); host caps and load ceilings are not in this config: they come from `fleet-config.json` (default `~/.claude/state/fleet-config.json`, or the `fleet_config` key), keyed by the host IDs returned by worker-list. A host not listed keeps the cap of 4. When that file is missing or unreadable, `--admit` refuses and one notice goes out until it reads again. Optional `leads` lists each lead's `name` and `terminal`; a lead whose `orca terminal show` fails gets one alert, rearmed when it answers again. Keep handles and machine names in the private config, never in this repository.

A waiter absent across ten minutes of observations with unread deliveries gets one alert, then rearms when the waiter returns or the inbox clears. The first pass records existing failed dispatches without alerting. After that, each new failed dispatch gets one alert. Every nonfinal dispatch, including children, counts toward host capacity. The watchdog only alerts; the coordinator follows Orca recovery before stopping or retrying anything. A CLI failure preserves state and fails the pass so the supervisor can report it. Without an independent minute scheduler this is an unactivated guard, not liveness coverage.

Optional `coordinator_watch` (`state_dir`, `offline_minutes` defaulting to 10, `alert_command`) belongs in the config of a backup host only, because a coordinator cannot report its own death. Each pass runs `git -C <state_dir> fetch -q origin` (ten second limit), then `git -C <state_dir> show origin/main:coordinator.conf`, and reads `coordinator <name>` from that text; on any git failure it falls back to `<state_dir>/coordinator.conf`. With no such line, or when this host is the named coordinator, it does nothing. Otherwise each pass runs `ssh -o BatchMode=yes -o ConnectTimeout=6 <name> true` with a ten second limit; a failed fetch alone does not count as the coordinator being offline. After `offline_minutes` of ssh failures it sends one alert, `coordinator <name> offline for <n> minutes; failover is manual, ask the owner`, by running `alert_command` with the text as its last argument (the private config picks the channel) and adding it to the normal notices even when `alert_command` fails, so configured runs and the log still see the line; a failed `alert_command` leaves `alerted` false and is retried on the next pass. When the coordinator answers again the state clears and one `coordinator <name> back` line goes out if an alert had been sent. A changed coordinator name resets the timer. This check runs first, before any Orca call, and saves its state at once. With `runs` empty it skips every Orca call, so a host without Orca passes cleanly. It only alerts: it starts nothing and fails over nothing.

Nothing is typed into a terminal. Notices queue in the state file and go to each run terminal as one `orchestration send`, at most every 600 seconds, oldest first with duplicates merged. A `lead pane gone`, `host cap exceeded`, `failed dispatch` or `inbox waiter absent` notice goes at once as a message, with whatever is queued, and before the worker_done sweep runs, so a slow sweep cannot delay it. Sweep notices (seats kept) join the digest after the sweep. A Verdict notice goes at once to the lead named by the owner record of its `author=` dispatch, and to the digest when there is no record. A failed send keeps the queue and retries on the next pass; an entry that still fails after 20 passes is dropped with a line on stderr. The send time and queue are saved in the state file, so a restart neither floods nor drops.

`script/coordinator-drain.sh` replaces the bare `orchestration check` in the coordinator's waiter. The waiter command becomes `script/coordinator-drain.sh --run <run> --wait`, so the drain is the waiter's parent and the `orchestration check --run <run> --wait` process is its child; a `waiter_pattern` that matches either command line still finds it. It takes the same arguments, prints the same JSON, and leaves out "Worker stopped without reporting" for a lead terminal (from `leads`, read from `FLEET_WATCH_CONFIG`, default `~/.config/fleet-watch/config.json`). Each dropped stop appends the lead's handle to `COORDINATOR_DRAIN_STATE` (default `~/.claude/state/coordinator-drain.log`), and fleet-watch turns that log into one digest line with a count per lead. A lead is matched by the message's `from` (also `handle` in the payload or `from_handle`), because the real message carries only `taskId` and `dispatchId` in its payload. It leaves out any `worker_done` whose `.relayed` marker holds exactly `sent`. With `--wait`, a batch where every message was dropped is not returned: the drain checks again, so the coordinator is not woken for nothing. It logs the number dropped on stderr. A worker's stop always passes. The drain writes nothing into the owner directory: the sweep is the only writer, and it reads mail the check already marked read.

Each pass also runs `worker-done-relay.sh sweep` once per run, and nothing else runs it. It reads the run's mail with `orchestration inbox --terminal run:<id> --limit 200 --full --json`, which lists handled and unhandled messages and marks nothing read (a script must never make a consuming `check`, so the drain is not on cron). Only a dispatch whose owner record has a `kind=` line is swept, so old one line records and the inbox history are never relayed, released or listed. The sweep keeps each `worker_done` as `<dispatch>.done.json` (written whole or not at all), relays it once to the lead in the owner record, and releases the seat only with proof. The relay is a message that carries the dispatch, branch, sha and the worker's own summary; the lead's terminal also gets a `check your inbox` nudge, and a failed nudge does not fail the relay. Nothing is typed into the coordinator's terminal, with or without an owner. `<dispatch>.relayed` holds `sending` before the send and `sent` after it. A pass that died in between leaves `sending`, and the next pass repeats the relay once (`resending`, then `sent`), so a crash causes at most one repeat. If that repeat died too, the marker becomes `sent` without a third send and one digest line says the relay may be lost. Only the exact word `sent` counts as relayed. A failed send removes the marker, keeps `done.json`, releases nothing and is retried on the next pass, with one digest line however many passes fail. A refused release is also one digest line and is retried. The owner record is the lead handle on line 1, then `kind=builder|reviewer`, `repo=owner/name`, `branch=` (builder) and one `pr=` line per PR (reviewer). The outcome is the `state` from `worker-show` (only `succeeded` can release; the `worker_done` payload has no outcome). Builder proof is `git ls-remote` showing the branch at `git rev-parse HEAD` of the dispatch worktree, taken from `worker-show`'s `workspace` (`<id>::<path>`), and only when that path is on the record's branch and has a remote of the record's repo. Reviewer proof is a Verdict first line on every PR with `head=` the PR head now and `verifier=` that dispatch, and the sweep makes no GitHub call below 500 requests remaining. A seat without proof stays and gets one digest line per dispatch. A remote worktree is not readable from here, so its seat stays until a lead releases it.

The owner record is written by `worker-done-relay.sh record --dispatch ID --lead HANDLE [--kind builder|reviewer --repo R --branch B --pr N]`, atomically. With `--lead` alone on an existing record it changes only line 1, so a lead handoff keeps the kind, repo, branch and pr lines. `start-remote-worker.sh` and `start-cursor-worker.sh` take `--owner-lead`, `--owner-repo` and `--owner-branch` (repo and branch together make `kind=builder`), run `worker-start`, read the dispatch id from its output, call `record`, and print the start output unchanged. A failed record write warns and does not fail the start. `on-worker-done.sh` uses `--owner`, which defaults to `$ORCA_TERMINAL_HANDLE`, for the reviewer's record.

`script/on-worker-done.sh` reads host caps from `fleet-config.json` (default `~/.claude/state/fleet-config.json`, or `ON_WORKER_DONE_FLEET_CONFIG`). When that file is missing or unreadable it refuses and the message names the file. There is no fallback to the older `~/.config/fleet-watch/config.json`: a host that still has only that file must copy its `host_caps`, `host_load_ceilings` and `local_host` keys into `fleet-config.json`.
