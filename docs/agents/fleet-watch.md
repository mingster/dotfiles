# Fleet watchdog

Orca registration for scheduled fleet jobs (including this pass) lives in [Orca automations](orca-automations.md).

Run `python3 script/fleet-watch.py --config <private-json> --state <private-state>` every 5 minutes from a supervisor independent of the coordinator's inbox waiter. Configure `runs` with each run's `id`, `terminal` (coordinator handle) and `waiter_pattern` (a process pattern unique to that run); configure `host_caps` using the host IDs returned by worker-list. Optional `leads` lists each lead's `name` and `terminal`; a lead whose `orca terminal show` fails gets one alert, rearmed when it answers again. Keep handles and machine names in the private config, never in this repository.

Each pass appends one summary line to `~/.orca/logs/fleet-watch.log` (pass duration, backup stamp age when `backup.stamp` is set, heavy-gate wait medians, worktree cleanup round ages, and any worker-stall or issue-scan actions). It never logs terminal screen content.

Nothing is typed into a coordinator terminal by default. Notices queue in the state file and go to each run terminal as one `orchestration send`, at most every 600 seconds, with duplicates merged. A `lead pane gone`, `host cap exceeded`, `failed dispatch`, or `inbox waiter absent` notice goes at once as a message, carrying whatever is already queued. A Verdict goes at once to the lead named by the user record of its `author=` dispatch, or joins the digest when there is no record. A run may set `"typed": true` to keep the legacy `terminal send` path for that terminal only. `script/coordinator-drain.sh` filters "Worker stopped without reporting" for lead terminals from the coordinator's inbox check (`FLEET_WATCH_CONFIG` must name the same private json as fleet-watch's `--config`, including `leads`); fleet-watch turns `COORDINATOR_DRAIN_STATE` into one digest line with a count per lead. A worker's stop is never dropped.

Optional `worker_stall`: set `label_repo` to a GitHub repo where stalled-worker issues and labels are applied (`needs-elon` by default). When a live worker's terminal has had no `lastOutputAt` progress for 30 minutes, the pass runs `worker-stop` once then `worker-start --retry-of <dispatch>`; if progress is still missing after the label cooldown, it adds the `needs-elon` label to the PR whose number is on the worker row, or found by branch head lookup when the row has no number; otherwise it opens a fixed-title issue.

Optional `backup` (`stamp` path to the coordinator's `~/<agent-state>/.sync-ok`, `issue_repo` as `owner/name` for GitHub issues) opens at most one **open** issue with the fixed title `agent-state backup has not pushed for 30 minutes` when that stamp is older than 30 minutes; if that title already exists among open issues, it does not create another. Configure it on the host that runs the monitor pass for the coordinator. The log line includes `backup_age_s=…` and adds `backup_stale` when the age exceeds 10 minutes, so a blocked sync is visible before the issue opens.

Optional `pr_watch` (`repos: ["owner/name"]`, `stuck_minutes` defaulting to 30, optional `workflows` defaulting to all failed runs in `RUN_WINDOW`) watches open PRs for merges, Verdicts, Review receipts, and stuck checks or reviews, reruns a failed GitHub Actions workflow once, then opens an issue labelled `needs-elon` when it fails twice.

Optional `heavy_gate` (`hosts: {host: wait_log_path}`, `issue_repo` as `owner/name`, optional `median_limit_seconds` defaulting to 120) reads `wait_s=` lines from the last 24 hours (`HEAVY_GATE_WAIT_MEDIAN_MAX_AGE_SECONDS`), logs `heavy_gate_median_<host>=<seconds>`, and opens at most one open issue titled `heavy-gate median wait exceeds 2 minutes on <host>` when the median exceeds two minutes.

Optional `wrap_up` (`hosts: {host: log_path}`, `issue_repo` as `owner/name`, optional `stale_limit_seconds` defaulting to 1200) reads the last timestamp in each host's `wrap-up-scheduled.log`, logs `wrap_up_age_<host>=<seconds>` (and `wrap_up_stale_<host>` past 10 minutes), and opens at most one open issue titled `wrap-up last round stale on <host>` when older than 20 minutes.

Optional `issue_scan` (disabled unless `enabled: true`; `repos`, `repo_roots`, optional `pr_repos`, `host`, `startup_script` defaulting to `script/worker-startup.sh`) runs when Orca inventory, the usage gate and host admission pass. Receipt scans (`Checks`, `Review`, `Verdict`) take the newest comment per kind at an exact head by `createdAt` and accept an optional `main=` suffix on the first line. Open PRs without a Checks receipt at the head get `head-checks.sh` each pass until one posts or a check worktree lock is live (a publication stamp alone does not suppress retries). It starts at most one rework worker per new failing head when Checks fail, when Checks pass and Review or Verdict failed, or when `statusCheckRollup` still shows `FAILURE` after a workflow rerun recorded in `workflow_watch` from before the same pass (`workflow_notices` runs first and may request the rerun without starting rework until the next pass). Rework passes `--base-branch` and the failing receipt into the spec. At most two rework rounds per PR, then it adds `needs-redesign` (no third patch; the coordinator closes the PR and dispatches a redesign). It also starts eligible `ready-for-agent` issues (unblocked, with evidence and predicate, ordered `P0` and `P1` first, then FIFO).

`install-fleet-automations.sh` passes `--config` for `~/.claude/state/fleet-watch-elon.json` unless `FLEET_WATCH_CONFIG` is set. That file is the coordinator config. The host-caps file `~/.config/fleet-watch/config.json` has no `runs`. When the file fleet-watch was given is that stub and has no `runs`, the pass reads the coordinator file instead if that file has `runs`. A pass whose config still has no `runs`, and is not a backup host's `coordinator_watch`, exits non-zero and appends a log line naming that file (`config <path> has no runs; refusing this pass`) instead of `pass ok` and `no change`. Each pass copies `issue_scan.run` and `issue_scan.from_terminal` from `runs[0]`. When `issue_scan` is enabled, `agent` and `model` come from `usage-gate.py pick --role fullstack-dev`.

The same pass dispatches one verifier for open pull requests in `issue_scan.pr_repos` and `pr_watch.repos` (or `babysit.repos` when that list is set). A non-draft PR whose head-checks succeeded and whose head has no Verdict gets one `qa-sdet` verifier from `usage-gate.py pick --role qa-sdet`, skipping a pick whose agent and model equal the builder (`Builder: agent=… model=…` in the PR body, or the dispatch record). The fix worker and the Shipping run stay the existing `issue_scan` groups. Each verifier is once per head: the state file records the repo, the PR and the head sha, and a new push re-arms it. At most two verifiers run per pass (`babysit.per_pass_cap`, default 2). A PR that touches an owner-only path (`script/lib/protected-paths.sh` `check_owner_only_paths`) is reported to the coordinator and not dispatched. Drafts are skipped. The brief goes through `worker-startup.sh` and must pass `script/brief-lint.sh`. `python3 script/fleet-watch.py --config <private-json> --state <private-state> --babysit-dry-run` lists the actions and starts nothing. This pass does not merge. `script/ship.sh` stays the shipping run for a head that already has a passing Verdict.

`script/fleet-toolchain-check.sh` (also run from `elon-startup.sh` and `wrap-up.sh --fleet`) reports fleet hosts whose tools are missing or differ from the coordinator (above or below), and the coordinator when it is below the latest release. Peers follow the coordinator, never the highest version in the fleet.

On the coordinator, each run also writes its versions to `~/agent-state/fleet-floor.json`, which `sync.sh push` carries to the other hosts. At session start, `state-of-play.sh` runs `script/session-sync.sh`. It fast-forwards the main checkout of the project and of `~/dotfiles` when that checkout is on main, clean and behind, leaves a dirty or diverged one alone (and says so), and names each local tool below the floor. It gives up on a fetch after 5 seconds and always exits 0, so an offline host still starts.

If `orca orchestration inbox` or `orca ... worker-list` fails or times out, one line reports that Orca could not be read and that pass skips worker inbox alerts (waiter, capacity, failed dispatch) and `issue_scan`; backup and other checks still run.

Wake path (#970). The coordinator arms one inbox waiter per delivery with `--timeout-ms 3600000`, so nothing else may depend on a short poll. Every wake reaches the run terminal as inbox mail: a worker settling arrives as its own `worker_done` or `escalation`, and fleet-watch sends everything else (failed dispatch, host cap, lead pane gone, stalled worker, ship or rework due, red main, absent waiter) with `orchestration send --to <run terminal>`, at once when urgent and otherwise within 600 seconds. A live waiter with unread mail raises no alert however long it waits; a dead one raises `inbox waiter absent` after ten minutes. `script/tests/fleet-watch-wake.test.sh` pins all three.

A waiter absent across ten minutes of observations with unread deliveries gets one terminal wake, then rearms when the waiter returns or the inbox clears. The first pass records existing failed dispatches without alerting. After that, each new failed dispatch gets one alert. Every nonfinal dispatch, including children, counts toward host capacity. The watchdog only alerts unless `worker_stall` or `issue_scan` is enabled; the coordinator follows Orca recovery before stopping or retrying anything. A CLI failure preserves state and fails the pass so the supervisor can report it. Without scheduling the pass every five minutes this is an unactivated guard, not liveness coverage.

Optional `coordinator_watch` (`state_dir`, `offline_minutes` defaulting to 10, `alert_command`) belongs in the config of a backup host only, because a coordinator cannot report its own death. Each pass runs `git -C <state_dir> fetch -q origin` (ten second limit), then `git -C <state_dir> show origin/main:coordinator.conf`, and reads `coordinator <name>` from that text; on any git failure it falls back to `<state_dir>/coordinator.conf`. With no such line, or when this host is the named coordinator, it does nothing. Otherwise each pass runs `ssh -o BatchMode=yes -o ConnectTimeout=6 <name> true` with a ten second limit; a failed fetch alone does not count as the coordinator being offline. After `offline_minutes` of ssh failures it sends one alert, `coordinator <name> offline for <n> minutes; failover is manual, ask the owner`, by running `alert_command` with the text as its last argument (the private config picks the channel) and adding it to the normal notices even when `alert_command` fails, so configured runs and the log still see the line; a failed `alert_command` leaves `alerted` false and is retried on the next pass. When the coordinator answers again the state clears and one `coordinator <name> back` line goes out if an alert had been sent. A changed coordinator name resets the timer. This check runs first, before any Orca call, and saves its state at once. With `runs` empty it skips every Orca call, so a host without Orca passes cleanly. It only alerts: it starts nothing and fails over nothing.
