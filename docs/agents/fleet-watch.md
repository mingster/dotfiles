# Fleet watchdog

This page describes the current single pass. The target design, and the feature freeze until it lands, is in [Fleet watch design](fleet-watch-design.md). Read it before changing fleet watch.

Orca registration for scheduled fleet jobs (including this pass) lives in [Orca automations](orca-automations.md).

Run `python3 script/fleet-watch.py --config <private-json> --state <private-state>` every 5 minutes from a supervisor independent of the coordinator's inbox waiter. Hand-kept keys: `repo_roots`, `host_caps`, `backup.stamp`, `heavy_gate.hosts`, `wrap_up.hosts`. `repo_roots` is the list of checkout paths on this machine. `host_caps` maps a host name to a count. A worker-list host that is an Orca environment id counts on that environment's name. The other three are the per-host paths that turn that monitor on. Each pass reads the coordinator Run id and terminal from `orchestration run-list --full` and `orchestration run-show --full`, and reads each repo `owner/name` from the `origin` remote of a `repo_roots` path. A pass that finds no coordinator Run logs `no coordinator run`, leaves notices queued, and exits 0. A backup host still sets `coordinator_watch`, which is not a hand-kept key. Keep paths and host ids in the private config, never in this repository.

Each pass appends one summary line to `~/.orca/logs/fleet-watch.log` (pass duration, backup stamp age when `backup.stamp` is set, heavy-gate wait medians, worktree cleanup round ages, and any worker-stall or issue-scan actions). It never logs terminal screen content.

Nothing is typed into a coordinator terminal by default. Notices queue in the state file and go to each run as one `orchestration send --to run:<id> --from <run terminal>`, at most every 600 seconds, with duplicates merged. That terminal is the sender fleet watch already uses for worker starts. The send does not pass the receiver as `--from`. A successful send logs `sent=<n>`. A failed send logs the Orca error code. A notice still unsent after 24 hours is dropped. A `lead pane gone`, `host cap exceeded`, `failed dispatch`, or `inbox waiter absent` notice goes at once as a message, carrying whatever is already queued. A Verdict goes at once to the lead named by the user record of its `author=` dispatch, or joins the digest when there is no record. A run may set `"typed": true` to keep the legacy `terminal send` path for that terminal only. `script/coordinator-drain.sh` filters "Worker stopped without reporting" for lead terminals from the coordinator's inbox check (`FLEET_WATCH_CONFIG` must name the same private json as fleet-watch's `--config`); fleet-watch turns `COORDINATOR_DRAIN_STATE` into one digest line with a count per lead. A worker's stop is never dropped.

When a coordinator Run exists, fleet watch records the dispatch id of each verifier, rework worker and scanned issue it starts. When a verifier or rework worker it started has had no `lastOutputAt` progress for 30 minutes, the pass runs `worker-stop` once then `worker-start --retry-of <dispatch>`. A failed stop or start is parked and reported once, with the first line of Orca's error message. A usage-gate or host-cap refusal is logged with its reason and retried. If the replacement is still silent after another 30 minutes, the dispatch is parked and reported once. The parked row names that worker's repo, from its checkout, or `mingster/agent-state` when the row has no repo. Any other stalled worker gets one notice on its first stalled window and is never labeled. Nudge, stop and release (#1842, owner Q6 A): a stalled issue builder, or a worker fleet watch did not start, climbs a ladder kept in `stall_ladder` in the state file. The first stalled pass only records the stall. With no new commit for 2 stall windows, the worker gets one nudge in its terminal. Only a nudge that was delivered starts the last window, so a worker whose terminal cannot be reached is never stopped. A settled or released worker leaves the ladder. A remote worker's transcript is read on every pass, its windows count from its last tool activity, and new activity takes it off the ladder. With still no new commit after 3 windows, and at least one window after the nudge, the pass runs `worker-stop` and `worker-release`, sets its card to `archived`, puts its issue back in `ready-for-agent` (only when it has no open PR) and sends one notice. Terminal output after the nudge does not reset the count; a new commit does. The stop, release and archive go through `stop_and_release_stalled`. A dispatch under the agent-state done hold (#1849) never climbs the ladder. A worker that holds unpushed commits or changed files is never stopped: it gets one notice instead (`stall_hold`). A remote worker counts as holding work, since its checkout cannot be read here, so it is nudged but never stopped. A worker waiting on a coordinator answer is skipped. Verifier and rework workers fleet watch started keep the restart above. The coordinator can still recover any worker by hand with `~/dotfiles/.agents/skills/orca-team/worker-watch.sh`. A remote worker is judged by its transcript, not by the server clock: fleet watch reads it with `orchestration worker-read --environment`, and a worker with tool activity inside the stall window is not flagged. A failed read is tried once more in the same pass. A transcript that still cannot be read to its end is `unknown`, retried on the next pass, and never flagged or stopped.

`backup.stamp` is the path to the coordinator's `~/<agent-state>/.sync-ok`. When that stamp is older than 30 minutes the pass opens at most one **open** issue in `mingster/agent-state` with the fixed title `agent-state backup has not pushed for 30 minutes`; if that title already exists among open issues, it does not create another. Configure it on the host that runs the monitor pass for the coordinator. The log line includes `backup_age_s=…` and adds `backup_stale` when the age exceeds 10 minutes, so a blocked sync is visible before the issue opens.

Open PRs in each repo from `repo_roots` are watched for merges, Verdicts, Review receipts, and checks or reviews stuck for 30 minutes. A failed GitHub Actions workflow is rerun once per head. A second failure on that head does not open an issue.

`heavy_gate.hosts` maps a host id to its wait log. The pass reads `wait_s=` lines from the last 24 hours (`HEAVY_GATE_WAIT_MEDIAN_MAX_AGE_SECONDS`), logs `heavy_gate_median_<host>=<seconds>`, and opens at most one open issue in `mingster/agent-state` titled `heavy-gate median wait exceeds 2 minutes on <host>` when the median exceeds two minutes.

With `board_stale_check` set to true in the private config, a pass runs the `board-done.py --fleet` dry run at most once an hour (`board_stale_check_seconds`). A card it would move to Done that is still listed an hour later gets one notice (at most five per pass): a settled dispatch whose worktree still shows in-progress or in-review (#1160). A failed dry run changes nothing and is tried again later.

Each pass counts the `.md` files in `changelog.d/` (README excluded) in every `repo_roots` checkout and sends one notice when a repo holds more than 50 (config key `changelog_fragment_warn`). It repeats only when the count doubles, and a count back under the limit resets it (#1161). Compile the fragments before the next deploy.

`wrap_up.hosts` maps a host id to its `wrap-up-daily.log` (wrap-up runs twice a day since 2026-11-26, so set `wrap_up.stale_limit_seconds` to 93600; the 10 minute `wrap-up-scheduled.log` no longer gets written). The pass reads the last timestamp, logs `wrap_up_age_<host>=<seconds>` (and `wrap_up_stale_<host>` past 10 minutes), and opens at most one open issue in `mingster/agent-state` titled `wrap-up last round stale on <host>` when older than 20 minutes.

Issue scan runs whenever a coordinator Run exists. Its repos are the origin of each `repo_roots` path, and the startup script defaults to `script/worker-startup.sh`. It runs when Orca inventory and the usage gate pass. Host admission decides where the next issue starts. Shipping a ready pull request does not wait on that admission. Receipt scans (`Checks`, `Review`, `Verdict`) take the newest comment per kind at an exact head by `createdAt` and accept an optional `main=` suffix on the first line. Open PRs without a Checks receipt at the head get `head-checks.sh` each pass until one posts or a check worktree lock is live (a publication stamp alone does not suppress retries). A refused local admission does not start head-checks. A spawn that fails is parked for that head until the head changes or the config file's modification time changes. It starts at most one rework worker per new failing head when Checks fail on the code, or when `statusCheckRollup` still shows `FAILURE` after a workflow rerun recorded in `workflow_watch` from before the same pass (`workflow_notices` runs first and may request the rerun without starting rework until the next pass). Rework passes `--base-branch` and the failing receipt into the spec. The receipt goes in whole up to 20000 characters with its comment link (a longer one is cut with a note), and a Checks FAIL starts with the failing step name and that step's last 40 lines (#1684). A Checks FAIL that is a host fault, or whose database step ran no tests, prints a rerun line and starts no rework. A Review or Verdict FAIL at the head is a digest line (`FAIL: send to architect-pm`), never an automatic rework (#1209). At most two rework rounds per PR. When the head is still red after the second round, it adds `needs-redesign` and sends one notice (no third patch). It does not open a `needs-elon` issue for a workflow that failed twice. The coordinator closes the PR and dispatches a redesign. It also starts eligible `ready-for-agent` issues (unblocked, with evidence and predicate, ordered dotfiles issues first, then P label, size and age, as in [Labels](labels.md)). One pass starts every eligible issue the host caps and the usage gate allow, re-checking the usage gate before each start and moving on after a failed, deferred, live or skipped candidate. It skips an issue that an open PR already closes, refs or is branched for, or that a live `#<n>|` worker holds. It also skips an issue whose body names an open blocker: a `Blocked by #n` line (or `owner/repo#n`), or an item under a `## Blocked by` heading. The log line `issue_blocked=<n>:by=<blocker>` names it. A blocker whose state gh cannot read skips the issue for that pass (`issue_blocker_unknown=`). Blocked issues do not count as ready supply. The issue is picked up on the first pass after the blocker closes, with no label change (#1788). A brief-lint failure removes `ready-for-agent` and adds `needs-triage`; a second failure adds an `issue_lint_stuck=<n>` digest line. A refused local admission starts the issue on the first `host_caps` host that still admits it and has a repo mapping for that repo. A worker-list host id that is an Orca environment id counts on that environment's name, which is the `host_caps` key. The environment list is read once per pass. A `worker_done` with outcome succeeded and green pull-request checks releases that worker, so the seat is free on the next admission in the same pass. A rework started only because the pull request no longer merges cleanly does not count toward the two-round cap. A ready pull request starts `ship.sh` in that pass, including when the local host is over its cap. GitHub `mergeable` UNKNOWN does not block that start. `ship.sh` rereads UNKNOWN.

Placement key `browser_hosts` (a list of host names, like `grok_hosts`): the hosts where the Playwright browser launches. `worker-placement.py` never picks a host outside it for a start whose `Worker role:` stamp is `release-manager` or `qa-sdet`. `worker-startup.sh --on ENV` for such a start exits 4 naming `browser_hosts` when ENV is not listed, unless `--force-host REASON` is given. A fleet config with no `browser_hosts` key keeps today's behaviour (no refusal). The list holds private host names, so it lives in the private fleet config, not in this repository (#1756).

Placement key `light_only_hosts` (a list of host names): light-only hosts take light work only; heavy steps are refused there (#1965). `worker-placement.py` never places a heavy start on one (a brief with `Heavy: yes`, a release-manager role, or one that names Playwright, regression, xcodebuild, build-and-test.sh, a `bun run build` or a full tsc). When only light-only hosts have room it prints `worker-placement: heavy start held (light-only hosts: ...)` and places nothing. `heavy-gate.py gate` on such a host refuses a heavy command (those steps, a full tsc or a database step) with one line and exit 3, so the worker pushes and a heavy host runs it. No key keeps today's behaviour.

Head checks hold (#1844). A head checks run sends its database step to the database host (`head_checks_remote.host`), and that host's heavy gate samples its own free memory against the 20% floor. For the whole step, from before the gate wait to the end, `head-checks.sh` holds `~/orca/workspaces/<repo>/_db-<host>_<dir>.lock` on the host that runs the checks. While a live process holds that lock, `admit()` refuses the host with `head checks hold the heavy gate on <host> (<lock>)`. The issue scan then places the start on the next admitting host (log `issue_scan_refused_<host>=head checks hold the heavy gate on <host>`) or, with none left, holds it for a later pass. A start with no `--on` follows the same rule: `worker-placement.py pick` skips the held host (stderr `skip <host> (head checks hold the heavy gate: <lock>)`, refusal entry `<host>=heavy-gate-held`). An explicit `--on <host>` is not refused. A lock whose pid has exited does not count, and only locks on the host running fleet watch or the pick are seen. The match key is `<host>__`, so it relies on the remote dir being absolute, as it is in `head_checks_remote`.

Idle seats start a triage worker. When a pass has open seats (the count issue scan already uses) and no eligible `ready-for-agent` issue, and a repo has open `needs-triage` or `ready-for-human` issues, the pass starts one architect-pm triage worker for that repo on a model family other than the builder's. It starts at most one per repo every `issue_scan.triage_interval_hours` (default 2), recorded as `issue_scan_triage_at` in the state file. It also skips, urgent or not, when the backlog is the one the last triage start saw (same issue numbers, none with `updatedAt` after that start), recorded as `issue_scan_triage_seen` (#1723). The brief is `templates/agent-team/docs/agents/triage-worker-brief.md`. The log line carries `triage_start=<backlog count>`, or `triage_skip_no_backlog`, `triage_skip_recent`, `triage_skip_unchanged`, `triage_skip_no_seat`, `triage_pick_blocked` or `triage_fail`. The coordinator then decides the returned questions and relabels `ready-for-agent` (`team.md`, Idle seats). A pass where an eligible issue exists but none starts does not trigger it.

`install-fleet-automations.sh` passes `--config` for `~/.claude/state/fleet-watch-elon.json` unless `FLEET_WATCH_CONFIG` is set. That file holds the hand-kept keys. The host-caps file `~/.config/fleet-watch/config.json` is not the scheduled config. A pass with a coordinator Run copies that Run onto issue scan, which is on for the pass, and takes `agent` and `model` from `usage-gate.py pick --role fullstack-dev`. Every gate call from fleet-watch (the issue scan check and the picks) passes `--auto`, which is how a start says it is automatic: only then does the daily cap block. Each refused provider writes one `usage_gate_refused provider=… verdict=… reason="…" reading_age_min=…` line per pass to `fleet-watch.log`. After 30 minutes of refusals while the refused provider has over 20 points of headroom, the coordinator gets one notice (settings in `script/usage-gate.config.json`). A pass where the gate refuses nothing resets the clock.

The same pass dispatches one verifier for open pull requests in the repos from `repo_roots`. A non-draft PR whose head-checks succeeded, whose head has a `Review: PASS` (or whose repo has no online review runner, #1321) and whose head has no Verdict gets one `qa-sdet` verifier from `usage-gate.py pick --role qa-sdet`, skipping every pick in the builder's model family (`Builder: agent=… model=…` in the PR body, or the dispatch record; sonnet and opus are one family). An exited verifier with no Verdict at that head is not live. When the verifier fleet-watch recorded for a head was stopped, failed, cancelled or is gone from a non-empty worker list, and the head has no Verdict and no other live verifier, the pass releases it and starts one fresh verifier; a second death parks the head (#1932). An exited or abandoned dispatch and a remote one with no terminal count as dead too. A dispatch the stall pass restarted, still owes a restart or parked is left to it, a stopped stall restart parks the head, and a done hold (below) keeps the dispatch unreleased. The fix worker stays in the existing `issue_scan` group. Each verifier is once per head: the state file records the repo, the PR and the head sha, and a new push re-arms it. A live verifier on the same PR blocks a start even when the state file has no record of it (`verifier-live`). `worker-startup.sh` refuses a second verifier for the same PR at the same head (exit 2) unless given `--allow-overlap REASON`; another head, or a brief naming no head, still warns and starts (#1960). Right before each start the open pull request list is read again, not the pass's cached list, and a PR no longer open is skipped (`not-open`, #1706). An unreadable list skips that PR for this pass (`state-unknown`). At most two verifiers run per pass (`babysit.per_pass_cap`, default 2). A PR that touches an owner-only path (`script/lib/protected-paths.sh` `check_owner_only_paths`) is reported to the coordinator once per head and still gets its verifier; only the ship waits for the owner. Drafts are skipped. The list is filtered to open PRs before any per PR work: a merged or closed PR gets no line, and the closed list is read only to release a live verifier that names a PR no longer open (`verifier-released`, #1841). A PR whose builder family cannot be resolved is refused (`unknown-builder-family`, log `unknown_builder=<pr>`) on three passes, then gets one notice and is skipped (`unknown-builder-parked`) until its head changes (`babysit_unknown_builder` in the state file, #1841). A head with `Review: FAIL` gets no verifier (`needs-fix`), and `script/pr-review.sh` drops its own result when another run posted a Review or Verdict on the same head while it was reviewing, so one head never carries two cold Reviews (#1841). With `babysit.standing_verifier` set (off by default), one standing antigravity verifier per configured trial host takes up to 5 PRs, falls back to a fresh verifier when its wake probe fails, and logs to a trial log (`--trial-summary`). The brief goes through `worker-startup.sh` and must pass `script/brief-lint.sh`. The verifier and fixer briefs say fleet-watch starts ship.sh for a ready head. `python3 script/fleet-watch.py --config <private-json> --state <private-state> --babysit-dry-run` lists the actions and starts nothing. Shipping a ready head is `script/ship.sh`, started from the issue-scan pass above.

Tiers (#1730, one week trial to 2026-12-01, `docs/agents/team.md` Tiers row in the template). `script/pr-tier.py` labels each open PR from its `files` (path, additions, deletions) and the pass reads it as `pr_tier`. A list that may be cut off (100 files), a missing line count, a protected path or an empty list is tier 2. Tier 0 (only test files and docs, 150 lines or fewer): with a Review PASS at the head and green required Checks the PR is `ready` with no Verdict, the issue scan auto-ship starts `ship.sh` at once (no 15 minute wait), and the babysit pass starts no verifier (`tier0-ship`). When fleet-watch does not auto-ship the repo, or the auto-ship already tried this head and the PR is still open, the old rule applies and a verifier starts. `ship.sh` takes a tier 0 PR through its docs lane: a cold `Review: PASS head=<head>` (or a Verdict) at the head, green Checks, the protected path checks. Tier 1 (50 code lines or fewer, no UI file): the babysit pass sorts these PRs first, and their verifiers do not count against `babysit.per_pass_cap`; the usage gate, host placement and parking still apply. Tier 2 is unchanged. Weekly audit: once per ISO week and repo the pass picks up to 5 random tier 0 PRs merged in the past 7 days that `~/agent-state/tier0-audit.tsv` (`TIER0_AUDIT_LOG`) does not list yet, appends them there, and files one issue `tier 0 audit <ISO week>` labelled `ready-for-agent` and `role:qa` (so the issue scan starts a qa-sdet, not a builder) with the PR list and an Acceptance for a qa-sdet verifier. It starts no worker and claims no merged PR. The issue body repeats each PR's `Builder: agent= model=` line once; when the issue scan starts the audit worker it asks the usage gate for a qa-sdet of another model family than those builders (`--avoid-family`), the same rule as the verifier start (#1765). With no other family available it starts the same family and the brief tells the auditor to add `same-family-different-model` as the second line of each Audit comment, without asking. It files nothing when an issue with that title exists (open or closed) or when no tier 0 PR merged. The log rows are written before the issue and cut again when the issue is not created. A failed fetch, issue lookup, log write or issue create leaves the week open for the next pass. The verifier posts `Audit: PASS merged=<sha>` or `Audit: FAIL merged=<sha>` on each PR, never a `Verdict:` line. `script/tier0-audit.py report --repo <owner/name>` (also in `team-audit.sh --report`) lists each pick with PASS, FAIL or pending and the FAIL rate against the 5 percent bar. `babysit.tier0_audit: false` turns the audit off.

A failed dispatcher start is tried once. The kinds are a verifier (repo, PR, head), a rework (those plus the round), a scanned issue (repo, issue, `updatedAt`), a head-checks spawn (repo, PR, head) and a stall restart (dispatch id). The pass parks that key, sends one notice with the first line of Orca's `error.message`, and does not try it again until the key changes or the config file's modification time changes. A usage-gate or host-cap refusal (exit 3 or 4) is logged with its reason and retried. Parked keys, and the `failed`, `stall_stopped` and `babysit` rows for that PR or issue, are dropped when a pass lists the PR or issue as closed. A fetch that fails leaves those rows in place.

`script/fleet-toolchain-check.sh` (also run from `elon-startup.sh` and `wrap-up.sh --fleet`) reports fleet hosts whose tools are missing or differ from the coordinator (above or below), and the coordinator when it is below the latest release. Peers follow the coordinator, never the highest version in the fleet.

On the coordinator, each run also writes its versions to `~/agent-state/fleet-floor.json`, which `sync.sh push` carries to the other hosts. At session start, `state-of-play.sh` runs `script/session-sync.sh`. It fast-forwards the main checkout of the project and of `~/dotfiles` when that checkout is on main, clean and behind, leaves a dirty or diverged one alone (and says so), and names each local tool below the floor. It gives up on a fetch after 5 seconds and always exits 0, so an offline host still starts.

If `orca orchestration inbox` or `orca ... worker-list` fails or times out, one line reports that Orca could not be read and that pass skips worker inbox alerts (waiter, capacity, failed dispatch) and `issue_scan`; backup and other checks still run.

Worker signals (#1741). Each pass flags a live worker by stall signals, not age. A run on its branch that has been `in_progress` for more than 15 minutes sends one urgent notice naming the run and its minutes (check the step log: slow or hung). A worker with no new push (the newest run head on its branch) and no new terminal output for 15 minutes sends one idle notice. A signal does not repeat until it clears and fires again. `worker_signals.limit_seconds` overrides the 900 second limit. A background wait inside a worker is not visible to fleet-watch, so the CI run is the proxy for it.

Worker time limits and hung checks (#1978). `worker-startup.sh` writes a start line to `~/.orca/logs/worker-durations.jsonl` (`WORKER_DURATIONS_LOG` overrides). Each pass writes a start line for a live worker it has not seen (start = that pass), adds role and size, and writes the end line on `worker_done` or when the row stops being live, so an end time is accurate to one pass. A live worker past 60 minutes (soft) or 90 minutes (hard) sends one urgent notice per level; `worker_limits.soft_minutes`, `hard_minutes` and `types["role/size"]` override them. Exempt: `elon`, `coordinator`, `support-csm`, `release-manager` and titles containing `regression`. The pass releases nothing. Report: `python3 script/worker-durations.py`. Separately, an open PR's GitHub Actions job in progress past its limit has its run cancelled, then rerun once the cancel finishes; if it runs past the limit again, one urgent notice. The limit (`ci_job_limit_seconds`) is 1.5 times the p90 duration of the check's 30 most recent successful runs in the fetched PRs when there are 10 or more, else 30 minutes, since a fixed 20 minutes cancelled healthy 19 to 21 minute `script-tests` runs. Repos are the babysit repos. Rules: `team.md`, Worker time limits.

One scheduler (#1838). The Orca automation `fleet-watch` on the coordinator host runs every pass, every 5 minutes, through `script/automation-precheck-wrapper.sh` with a 280 s timeout. The background loop (#1204) is retired, and `elon-startup.sh` only reports whether the automation is enabled. `script/install-fleet-automations.sh` creates the automation enabled on the coordinator and then keeps the owner's choice: a re-install never turns a disabled fleet-watch back on. Any pass (the automation or a manual run) takes an exclusive lock on `<state>.lock` and exits 0 when another pass holds it, so two passes never read the same state and each start a verifier for one PR head (#1706). Each pass is a fresh `python3` process, so a pulled code change loads on the next pass. Its own starts carry no `--from`, name the repo as `--repo id:<id>` (`path:` only when Orca cannot name the checkout), and skip an issue, rework or verifier start when a live worker already has the same `#<issue or PR>|<role>` title. Judgement items stay digest lines. `elon-tick.py` check W1 flags the automation when it is disabled, missing, or has no `phase=end` line in `~/.orca/logs/fleet-watch.log` within 10 minutes.

Pass deadline (#1838). A pass stops new work 250 s after it began (`PASS_HARD_END`), ahead of the 280 s timeout, so the timeout never kills it mid worker start. The check is cooperative: before each babysit row, each issue scan PR row, repo and candidate, and each phase after babysit (audit, issue_scan, stall, signal, nudge). A start already begun always finishes. Deliver and save still run, and the summary line carries `pass deadline 250s: skipped <phases>` plus `babysit_deadline=<PR>` or `issue_scan_deadline` where a loop stopped. The start budget (`START_FINISH_BY`, 140 s) is unchanged. A verifier or fixer start, which skips that budget, is still held when the time so far plus its cost (45 s, or 105 s for antigravity) plus a 25 s tail (`START_TAIL`, the audit, issue scan, deliver, save and exit after the last start) would pass 250 s; it logs `start_deadline=<PR>` and the next pass starts it (#1820).

Answered asks (#1838, #1947). The inbox `handled` flag only means read, so it is no answer. The unanswered question digest skips an ask whose id `script/orca-reply.sh` recorded in `~/.local/state/agent-team/answered-asks.txt` (`ORCA_REPLY_ANSWERED_FILE`) after `reply` returned `answer_conflict`.

Wake path (#970). The coordinator arms one inbox waiter per delivery with `--timeout-ms 3600000`, so nothing else may depend on a short poll. Every wake reaches the run terminal as inbox mail: a worker settling arrives as its own `worker_done` or `escalation`, and fleet-watch sends everything else (failed dispatch, host cap, lead pane gone, stalled worker, ship or rework due, red main, absent waiter) with `orchestration send --to run:<id> --from <run terminal>`, at once when urgent and otherwise within 600 seconds. A live waiter with unread mail raises no alert however long it waits; a dead one raises `inbox waiter absent` after ten minutes. `script/tests/fleet-watch-wake.test.sh` pins all three.

A waiter absent across ten minutes of observations with unread deliveries gets one terminal wake, then rearms when the waiter returns or the inbox clears. The first pass records existing failed dispatches without alerting. After that, each new failed dispatch gets one alert. A dispatch already alerted, or one that is released or settled, is not sent again. Every nonfinal dispatch, including children, counts toward host capacity. With a coordinator Run the pass also restarts a stalled worker it started and runs issue scan; the coordinator follows Orca recovery before stopping or retrying anything. A CLI failure preserves state and fails the pass so the supervisor can report it. Without scheduling the pass every five minutes this is an unactivated guard, not liveness coverage.

A settled `release_unknown` row stops counting on this host when the pass can prove the worker is gone. The dispatch state is succeeded, stopped, or failed. No process has the workspace path as its working directory or as an argument. The worktree is missing, or `git status --porcelain` is empty. A failed check, a worker on another host, or any other terminal state stays in the count. The host cap does not change.

Optional `coordinator_watch` (`state_dir`, `offline_minutes` defaulting to 10, `alert_command`) belongs in the config of a backup host only, because a coordinator cannot report its own death. Each pass runs `git -C <state_dir> fetch -q origin` (ten second limit), then `git -C <state_dir> show origin/main:coordinator.conf`, and reads `coordinator <name>` from that text; on any git failure it falls back to `<state_dir>/coordinator.conf`. With no such line, or when this host is the named coordinator, it does nothing. Otherwise each pass runs `ssh -o BatchMode=yes -o ConnectTimeout=6 <name> true` with a ten second limit; a failed fetch alone does not count as the coordinator being offline. After `offline_minutes` of ssh failures it sends one alert, `coordinator <name> offline for <n> minutes; failover is manual, ask the owner`, by running `alert_command` with the text as its last argument (the private config picks the channel) and adding it to the normal notices even when `alert_command` fails, so configured runs and the log still see the line; a failed `alert_command` leaves `alerted` false and is retried on the next pass. When the coordinator answers again the state clears and one `coordinator <name> back` line goes out if an alert had been sent. A changed coordinator name resets the timer. This check runs first, before any Orca call, and saves its state at once. With no coordinator Run it skips every Orca call, so a host without Orca passes cleanly. It only alerts: it starts nothing and fails over nothing.

Board relay on `worker_done` (#1842, `relay_done_board`). When a `worker_done` arrives and the worker left its card in another column, the pass sets `in-review` while its PR is open and `completed` when it has no PR or the PR is closed. A card already in `in-review`, `completed` or `archived` stays. A release by `release_green_successes` sets `completed` when the PR has merged. A worker stopped for a stall is set to `archived`, and `board-done.py` treats `archived` as final, like `completed`. Wrap up's `board-done.py --fleet --apply` round sets `completed` on any workspace with no live task and a merged or closed PR.
Remote `worker_done` reconcile (#1269). The coordinator rejects a relayed remote `worker_done` as `unknown_dispatch` or `unknown_task`, and neither rejected copy counts as accepted. A settled remote row gets a synthesized `worker_done` and is released. A rejected dispatch missing from `worker-list` is read with `worker-show --dispatch` and settled the same way. A succeeded PR worker whose checks are still pending keeps its synthesized `worker_done` each pass until `release_green_successes` releases it, so no hand `worker-stop` or `worker-release` is needed.
Agent-state done hold (#1849). A `worker_done` whose body names a path under `~/agent-state/` does not count until that path exists in the coordinator's `~/agent-state` checkout, or until the body names a commit sha that exists there (a PR head sha does not count). Each pass, before the remote reconcile, `update_done_holds` reads the newest `worker_done` of every dispatch that still has a release ahead, including a rejected remote copy (its text after `Original body:`). The concise inbox view cuts a body at 200 characters, so a cut body is read once with `inbox --full` and cached by message id in `done_hold_text`; a body that cannot be read holds with no notice until a later pass. A failing body sets `done_hold[<dispatch>]` (`reason`, `message_id`, `since`); a later passing `worker_done` clears it. `release_held` is the one gate. `release_green_successes`, the remote reconcile (before it synthesizes a `worker_done`), the board relay, the stall ladder (nudge, stop and release) and the babysit verifier releases (a closed PR, idle rework, a retired standing verifier) all skip a held dispatch. A pass whose hold check fails skips the reconcile and the release round; the stall ladder and babysit still run on the holds of the last pass. Exempt, because the worker failed at startup or its parent is gone and no `worker_done` is in play: `retry_startup_failed`, the failed verifier startup release in babysit (the release of any other dead verifier honours the hold), and `release_dead_followups`. The worker hears the reason once in its terminal (`--environment` for a remote row). The notice counts as sent only with a terminal handle, an environment for a remote row and no send error, recorded in `done_hold_notified`; otherwise it is tried again each pass and the coordinator hears `hold on <dispatch>: notice not delivered` once per message. A hold with no passing resend after one stall window sends the coordinator one urgent notice. Fleet watch never releases a held dispatch; the coordinator or a fixed resend does.

`worker_done` outcome fallback (#1858). The concise inbox view omits `outcome`. When neither the message nor its payload carries one, `_message_outcome` reads the matched worker row (`worker_settled_kind`, `succeeded` or `failed`), so a concise `worker_done` still releases a succeeded worker on green checks, and a failed worker is not released, not bounced on the PR body and does not move its board card. An explicit `outcome` on the message or payload always wins.

Startup failures (#1270). A start that reports `ready` can still fail seconds later at `agent_readiness` or `dispatch_input` (`terminal_exited`, `agent_not_in_foreground`, `timeout`). `worker-startup.sh` keeps reading `worker-show` through the readiness wait, for local and remote starts alike. On a startup failure it releases the dispatch (on its environment when remote) and retries once on the same task with `--task` and `--retry-of`, so no second task appears. `worker-list` rows of a failed remote dispatch carry no stage or error, so `fleet-watch` reads `worker-show` once for each failed own or follow-up row, caches the answer under `show_checked`, and retries a startup failure once. A failure at `server_record` or `settled` is not retried as a startup failure; a recorded verifier is still replaced once under the dead verifier rule above (#1932).

Duplicate verifiers (#1271). `fleet-watch` and `worker-startup.sh` read a bare `verify <pr>` title (`#<issue>|qa-sdet|verify <pr>`) as that PR, and `fleet-watch` also reads the worktree in the launch record of a remote dispatch, whose `worker-list` row has no checkout path. `warn_live_verifier` lists workers without `--terminal-state active`, because remote rows carry `terminalState: null`, and skips finished dispatches. A `qa-sdet` start never removes `ready-for-agent` from the issue it refs.

Standing verifier trial (#1272, turned off in #1308). The one day trial is off. `resolve_pass_config` does not copy `babysit.standing_verifier` from `~/.config/fleet-watch/config.json` when it adopts the coordinator state file, and `standing_settings` ignores `hosts: ["auto"]` (or an empty host list) so the standing verifier stays disabled unless explicit trial hosts are configured. A wake that does not happen, 5 PRs, or `ctx` at 70% stops and releases it on its environment and starts a fresh verifier in the same pass, with each step logged to `verifier-trial.tsv`.

Seats (#1273). `worker-placement.py` and `fleet-watch.py --admit` read the active coordinator Run, not every historical Run, when the config is the scheduled stub with no `runs`. A released worker holds no seat, even with unpushed work. A finished worker whose resource Orca no longer has holds none either, and neither does a dispatch that an earlier pass released (`auto_released`, `remote_reconciled`, `followup_released` in the state file; pass `--state`, or set `FLEET_WATCH_STATE` for placement). A start that fails before launching is removed from the recent starts with `worker-placement.py unrecord --host <host> --claim <id>` (the id `pick --record` returned; without `--claim` the newest start on the host goes), so it holds no seat for 5 minutes. A settled, exited worker (succeeded, failed, cancelled) holds no seat, released or not, unless it has unpushed work. A recent start is one pending seat and one worker's memory, and it stops counting once the inventory lists its dispatch (#1411).

Work order (#1281, owner 2026-11-21). The scripts enforce it, not the coordinator's memory. Hourly metrics (#1957): once an hour the log gets one `metrics hour=<UTC hour>` line for the hour that ended: `merged_per_h`, first pass PASS rate for Review and Verdict (`review_first_pass=a/b`), `wasted_starts` (start_unknown and duplicate same title dispatches, counted once per id, plus failed dispatches), `median_open_to_merge_h`, `mean_live` from the pass lines, and `cost: n/a` while no usage reading exists. `fleet-watch.py --metrics-digest 12` prints the last 12, and `wrap-up.sh` shows them under `Fleet metrics`. With `work_order.keep_target_until_go_live` true (#1655, default false) and today (Asia/Taipei) before `go_live_date`, `min_active` becomes `target_workers`: every pass under target with a free seat starts ready issues first, then verifiers (the babysit pass, every pass), then triage without waiting for `triage_interval_hours`, and the backlog sweep on its own interval. A missing or malformed `go_live_date` turns the switch off, and on or after `go_live_date` it does nothing. Every fleet-watch worker start (babysit and issue scan: ready issues, rework, triage, backlog sweep) hands `worker-startup.sh` the coordinator handle from `from_terminal` as `ORCA_TERMINAL_HANDLE` when the scheduled run has none, so starts never fail with `need --from` (#1640, #1655). Supply (#1689): with a `work_order` block, when free seats (`target_workers` minus live workers minus this pass's starts) outnumber the startable `ready-for-agent` issues across `issue_scan.repos`, fleet-watch starts one architect-pm supply worker (#1816: the count excludes ready issues this pass will not start, such as a started one, one with an open PR, a parked one or one with a live worker (named by its `#N|role` title, a spec `Refs #N`, or a `b<N>` or `w<N>` branch, #1960), as well as blocked ones; title `#0|architect-pm|supply`, brief `docs/agents/supply-worker-brief.md`). It triages `needs-triage` issues and files follow-ups from merged PRs of the last 7 days and Review or Verdict FAIL comments, each with Acceptance, Out of scope and a priority, labeled `ready-for-agent`. A live `#0|architect-pm` worker (supply, triage or backlog sweep) blocks it, it starts at most once per `triage_interval_hours`, it runs only on the coordinator when local admission passes and never takes a local seat this pass's ready issues need, and a supply start replaces that pass's triage worker. Every pass whose issue list succeeds queues `work order: N live (W working, V waiting on coordinator), supply S, <host> load L cap C` (S is the count of ready-for-agent issues this pass could start, L the host's 1 minute load per core); the digest dedupes equal lines and goes out at most every 10 minutes.

Forced supply (#1876, owner 2026-11-25). fleet-watch counts the passes in a row where the free seats outnumber the startable `ready-for-agent` issues (state key `work_order_short_passes`). A pass where supply fills the seats resets the count, and so does a supply start. Fill, deferral and stalls (#1778, owner 2026-11-24). Starts go toward `work_order.target_workers`, bounded by `host_caps`, `host_load_ceilings` and the usage gate. A ready issue that was not started this pass is deferred with a reason (`host_cap`, `placement`, or the start refusal) and logged as `issue_deferred=<n>:<reason>`. Delivered refusals and restarts (#1811). `worker-startup.sh` checks the issue named by the `#<n>|` title, not the first `Refs` line of the brief (an issue body often starts with `Refs <parent>`), and counts a merged PR only when it closes that issue with `Closes`, `Fixes` or `Resolves`. An issue in `issue_scan_started` with no open PR and no live `#<n>|` worker starts again once 30 minutes have passed since its start (`issue_scan_started_at`): a ready one starts in that pass, and an open one still labelled `status:進行中` gets `ready-for-agent` back so the next pass starts it. An unreadable PR list (log `issue_restart_skipped=<n>:pr_list`), an open blocker or a park still holds the issue, and a failed relabel keeps it in `issue_scan_started` for the next pass. Each restart logs `issue_restart=<n>:<ready|orphaned>` and sends one notice line.

Pass phases (#1820). Every `pass ok` line ends with `phases <name>=<seconds>,...` and, when the pass started workers, `starts=<seconds>,...` (one number per start). A pass the precheck wrapper stops with SIGTERM logs `pass killed <seconds>s; phases ...`, with the phase it was in listed last, and exits 143. Start budget (#1820). Each start site (issue start, auto ship, backlog sweep, supply, triage, rework) calls `start_allowed(cost)` once, after it picks the agent and before it writes any state. It is true while the seconds since `main()` began plus the cost fit `START_FINISH_BY` (140 seconds). The cost is `START_COST_AGY` (105 seconds) for an antigravity start that keeps `worker-startup.sh`'s 60 second sign in screen wait, and `START_COST_OTHER` (45 seconds) for any other start (the ship script counts as other). A held start logs `<site>_budget=<id>` (`issue_start_budget=<issue>`, `ship_budget=<pr>`, `backlog_sweep_budget=<repo or role>`, `supply_budget=<free>:<supply>`, `triage_budget=<repo>`, `rework_budget=<pr>`), writes no state, and counts nothing as started, failed, deferred or parked, so the next pass tries again: an auto ship leaves `shipped[head]` unset, and an issue start does not count toward the 3 pass deferral escalation. Verifier starts (one shot and standing) have no budget check (owner 2026-11-25, #1838, #1841): a PR with Review PASS at its head and no Verdict starts its verifier on the same pass, subject only to `script/usage-gate.py`, host caps and `babysit.per_pass_cap`. An antigravity verifier start (about 105 seconds) can therefore run a pass toward the 280 second kill. The budget changes no configured cap. `with_coordinator_handle` has no budget check and no grace: a start its site let through always runs, so the check cannot race it. With no `main()` clock (tests, direct calls) every start is allowed. `script/tests/test_fleet_watch_start_budget.py` pins it, and fails when `script/fleet-watch.py` gains a start call site that its tables do not list.

Signed out antigravity issue start (#1832). One release interface (#1958). Release means stop plus close: every fleet watch retire (a stalled worker, a green success, a dead follow up, a closed or idle verifier, a rework head, a standing verifier, a finished remote worker) calls `release_worker(rpc_call, row)`. It runs `worker-stop` and `worker-release` on the row's host and then here, then closes the worker's terminal on the host that holds it (`close_worker_terminal`). The coordinator's terminal and a terminal another live worker uses are never closed. A stop error other than `dispatch_not_found` stops there and closes nothing. The row comes from `fleet_rows`, which merges each host's own `worker-list` into the coordinator's rows: `_host` (the environment, empty for this host), `_state` (the host's dispatch state), `_host_terminal` (the host's terminal handle) and `_host_read` (False when that host could not be read). The host's `terminal`, `host` and `projection` fields are not copied, so a remote row stays remote for every other pass. A release counts as done only when it returns `closed` or `kept:no_handle`. Only the stall restart and the startup retry call `worker-stop` or `worker-release` directly, because they restart the worker instead of retiring it. A hand release uses `script/release-worker.sh <dispatch, task or terminal id fragment>` (`--live` for a live worker); it releases the one match on its host and confirms the terminal is gone from that host's terminal list. `script/tests/test_fleet_watch_release.py` pins it.

start_unknown reaper (#1962, #1947). A worker whose own host still lists it as `start_unknown` after 10 minutes gets its brief (`dispatch-show --preamble`) sent into its terminal once more, on that host. At 20 minutes, with that resend done, it is released through `release_worker`, its issue goes back to `ready-for-agent` (when it has an issue, a known repo and no PR), and the coordinator gets one Urgent line. A release that keeps the terminal for any reason but a missing handle is tried again next pass. A row whose host could not be read waits. The stall ladder leaves these dispatches to the reaper. The book is `start_unknown` in the state file.

Orphan terminal sweep (#1963, #1947). Every pass, after the reaper and before babysit, closes a terminal titled `#N|role` or `<job> run N`, or opened in an `auto-<job>-run-<n>` worktree, when no live worker row holds it (by terminal or worktree) and it has had no output for 15 minutes or more. A terminal with no output time stays open. It reads the pass rows, skips a host whose terminal or worker list cannot be read, and closes through `close_worker_terminal`, so the coordinator's and live terminals stay open. Worktrees stay for `wrap-up.sh`. `fleet-watch.py --config <file> --sweep-dry-run` lists what it would close and closes nothing. It needs no `--state` and takes no pass lock. A pass whose Orca inventory read fails runs neither the reaper nor the sweep.
