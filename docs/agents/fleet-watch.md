# Fleet watchdog

This page describes the current single pass. The target design, and the feature freeze until it lands, is in [Fleet watch design](fleet-watch-design.md). Read it before changing fleet watch.

Orca registration for scheduled fleet jobs (including this pass) lives in [Orca automations](orca-automations.md).

Run `python3 script/fleet-watch.py --config <private-json> --state <private-state>` every 5 minutes from a supervisor independent of the coordinator's inbox waiter. Hand-kept keys: `repo_roots`, `host_caps`, `backup.stamp`, `heavy_gate.hosts`, `wrap_up.hosts`. `repo_roots` is the list of checkout paths on this machine. `host_caps` maps a host id from worker-list to a count. The other three are the per-host paths that turn that monitor on. Each pass reads the coordinator Run id and terminal from `orchestration run-list --full` and `orchestration run-show --full`, and reads each repo `owner/name` from the `origin` remote of a `repo_roots` path. A pass that finds no coordinator Run logs `no coordinator run`, leaves notices queued, and exits 0. A backup host still sets `coordinator_watch`, which is not a hand-kept key. Keep paths and host ids in the private config, never in this repository.

Each pass appends one summary line to `~/.orca/logs/fleet-watch.log` (pass duration, backup stamp age when `backup.stamp` is set, heavy-gate wait medians, worktree cleanup round ages, and any worker-stall or issue-scan actions). It never logs terminal screen content.

Nothing is typed into a coordinator terminal by default. Notices queue in the state file and go to each run as one `orchestration send --to run:<id> --from <run terminal>`, at most every 600 seconds, with duplicates merged. That terminal is the sender fleet watch already uses for worker starts. The send does not pass the receiver as `--from`. A successful send logs `sent=<n>`. A failed send logs the Orca error code. A notice still unsent after 24 hours is dropped. A `lead pane gone`, `host cap exceeded`, `failed dispatch`, or `inbox waiter absent` notice goes at once as a message, carrying whatever is already queued. A Verdict goes at once to the lead named by the user record of its `author=` dispatch, or joins the digest when there is no record. A run may set `"typed": true` to keep the legacy `terminal send` path for that terminal only. `script/coordinator-drain.sh` filters "Worker stopped without reporting" for lead terminals from the coordinator's inbox check (`FLEET_WATCH_CONFIG` must name the same private json as fleet-watch's `--config`); fleet-watch turns `COORDINATOR_DRAIN_STATE` into one digest line with a count per lead. A worker's stop is never dropped.

When a coordinator Run exists, fleet watch records the dispatch id of each verifier, rework worker and scanned issue it starts. When one of those has had no `lastOutputAt` progress for 30 minutes, the pass runs `worker-stop` once then `worker-start --retry-of <dispatch>`. A failed stop or start is parked and reported once, with the first line of Orca's error message. A usage-gate or host-cap refusal is logged with its reason and retried. If the replacement is still silent after another 30 minutes, the dispatch is parked and reported once. The parked row names that worker's repo, from its checkout, or `mingster/agent-state` when the row has no repo. Any other stalled worker gets one notice and is never stopped or labeled; the coordinator recovers it with `worker-watch.sh`.

`backup.stamp` is the path to the coordinator's `~/<agent-state>/.sync-ok`. When that stamp is older than 30 minutes the pass opens at most one **open** issue in `mingster/agent-state` with the fixed title `agent-state backup has not pushed for 30 minutes`; if that title already exists among open issues, it does not create another. Configure it on the host that runs the monitor pass for the coordinator. The log line includes `backup_age_s=…` and adds `backup_stale` when the age exceeds 10 minutes, so a blocked sync is visible before the issue opens.

Open PRs in each repo from `repo_roots` are watched for merges, Verdicts, Review receipts, and checks or reviews stuck for 30 minutes. A failed GitHub Actions workflow is rerun once per head. A second failure on that head does not open an issue.

`heavy_gate.hosts` maps a host id to its wait log. The pass reads `wait_s=` lines from the last 24 hours (`HEAVY_GATE_WAIT_MEDIAN_MAX_AGE_SECONDS`), logs `heavy_gate_median_<host>=<seconds>`, and opens at most one open issue in `mingster/agent-state` titled `heavy-gate median wait exceeds 2 minutes on <host>` when the median exceeds two minutes.

`wrap_up.hosts` maps a host id to its `wrap-up-scheduled.log`. The pass reads the last timestamp, logs `wrap_up_age_<host>=<seconds>` (and `wrap_up_stale_<host>` past 10 minutes), and opens at most one open issue in `mingster/agent-state` titled `wrap-up last round stale on <host>` when older than 20 minutes.

Issue scan runs whenever a coordinator Run exists. Its repos are the origin of each `repo_roots` path, and the startup script defaults to `script/worker-startup.sh`. It runs when Orca inventory, the usage gate and host admission pass. Receipt scans (`Checks`, `Review`, `Verdict`) take the newest comment per kind at an exact head by `createdAt` and accept an optional `main=` suffix on the first line. Open PRs without a Checks receipt at the head get `head-checks.sh` each pass until one posts or a check worktree lock is live (a publication stamp alone does not suppress retries). A spawn that fails is parked for that head until the head changes or the config file's modification time changes. It starts at most one rework worker per new failing head when Checks fail, when Checks pass and Review or Verdict failed, or when `statusCheckRollup` still shows `FAILURE` after a workflow rerun recorded in `workflow_watch` from before the same pass (`workflow_notices` runs first and may request the rerun without starting rework until the next pass). Rework passes `--base-branch` and the failing receipt into the spec. At most two rework rounds per PR. When the head is still red after the second round, it adds `needs-redesign` and sends one notice (no third patch). It does not open a `needs-elon` issue for a workflow that failed twice. The coordinator closes the PR and dispatches a redesign. It also starts eligible `ready-for-agent` issues (unblocked, with evidence and predicate, ordered `P0` and `P1` first, then FIFO).

`install-fleet-automations.sh` passes `--config` for `~/.claude/state/fleet-watch-elon.json` unless `FLEET_WATCH_CONFIG` is set. That file holds the hand-kept keys. The host-caps file `~/.config/fleet-watch/config.json` is not the scheduled config. A pass with a coordinator Run copies that Run onto issue scan, which is on for the pass, and takes `agent` and `model` from `usage-gate.py pick --role fullstack-dev`. Every gate call from fleet-watch (the issue scan check and the picks) passes `--auto`, which is how a start says it is automatic: only then does the daily cap block. Each refused provider writes one `usage_gate_refused provider=… verdict=… reason="…" reading_age_min=…` line per pass to `fleet-watch.log`. After 30 minutes of refusals while the refused provider has over 20 points of headroom, the coordinator gets one notice (settings in `script/usage-gate.config.json`). A pass where the gate refuses nothing resets the clock.

The same pass dispatches one verifier for open pull requests in the repos from `repo_roots`. A non-draft PR whose head-checks succeeded and whose head has no Verdict gets one `qa-sdet` verifier from `usage-gate.py pick --role qa-sdet`, skipping a pick whose agent and model equal the builder (`Builder: agent=… model=…` in the PR body, or the dispatch record). The fix worker and the Shipping run stay the existing `issue_scan` groups. Each verifier is once per head: the state file records the repo, the PR and the head sha, and a new push re-arms it. At most two verifiers run per pass (`babysit.per_pass_cap`, default 2). A PR that touches an owner-only path (`script/lib/protected-paths.sh` `check_owner_only_paths`) is reported to the coordinator and not dispatched. Drafts are skipped. The brief goes through `worker-startup.sh` and must pass `script/brief-lint.sh`. `python3 script/fleet-watch.py --config <private-json> --state <private-state> --babysit-dry-run` lists the actions and starts nothing. This pass does not merge. `script/ship.sh` stays the shipping run for a head that already has a passing Verdict.

A failed dispatcher start is tried once. The kinds are a verifier (repo, PR, head), a rework (those plus the round), a scanned issue (repo, issue, `updatedAt`), a head-checks spawn (repo, PR, head) and a stall restart (dispatch id). The pass parks that key, sends one notice with the first line of Orca's `error.message`, and does not try it again until the key changes or the config file's modification time changes. A usage-gate or host-cap refusal (exit 3 or 4) is logged with its reason and retried. Parked keys, and the `failed`, `stall_stopped` and `babysit` rows for that PR or issue, are dropped when a pass lists the PR or issue as closed. A fetch that fails leaves those rows in place.

`script/fleet-toolchain-check.sh` (also run from `elon-startup.sh` and `wrap-up.sh --fleet`) reports fleet hosts whose tools are missing or differ from the coordinator (above or below), and the coordinator when it is below the latest release. Peers follow the coordinator, never the highest version in the fleet.

On the coordinator, each run also writes its versions to `~/agent-state/fleet-floor.json`, which `sync.sh push` carries to the other hosts. At session start, `state-of-play.sh` runs `script/session-sync.sh`. It fast-forwards the main checkout of the project and of `~/dotfiles` when that checkout is on main, clean and behind, leaves a dirty or diverged one alone (and says so), and names each local tool below the floor. It gives up on a fetch after 5 seconds and always exits 0, so an offline host still starts.

If `orca orchestration inbox` or `orca ... worker-list` fails or times out, one line reports that Orca could not be read and that pass skips worker inbox alerts (waiter, capacity, failed dispatch) and `issue_scan`; backup and other checks still run.

Wake path (#970). The coordinator arms one inbox waiter per delivery with `--timeout-ms 3600000`, so nothing else may depend on a short poll. Every wake reaches the run terminal as inbox mail: a worker settling arrives as its own `worker_done` or `escalation`, and fleet-watch sends everything else (failed dispatch, host cap, lead pane gone, stalled worker, ship or rework due, red main, absent waiter) with `orchestration send --to run:<id> --from <run terminal>`, at once when urgent and otherwise within 600 seconds. A live waiter with unread mail raises no alert however long it waits; a dead one raises `inbox waiter absent` after ten minutes. `script/tests/fleet-watch-wake.test.sh` pins all three.

A waiter absent across ten minutes of observations with unread deliveries gets one terminal wake, then rearms when the waiter returns or the inbox clears. The first pass records existing failed dispatches without alerting. After that, each new failed dispatch gets one alert. Every nonfinal dispatch, including children, counts toward host capacity. With a coordinator Run the pass also restarts a stalled worker it started and runs issue scan; the coordinator follows Orca recovery before stopping or retrying anything. A CLI failure preserves state and fails the pass so the supervisor can report it. Without scheduling the pass every five minutes this is an unactivated guard, not liveness coverage.

Optional `coordinator_watch` (`state_dir`, `offline_minutes` defaulting to 10, `alert_command`) belongs in the config of a backup host only, because a coordinator cannot report its own death. Each pass runs `git -C <state_dir> fetch -q origin` (ten second limit), then `git -C <state_dir> show origin/main:coordinator.conf`, and reads `coordinator <name>` from that text; on any git failure it falls back to `<state_dir>/coordinator.conf`. With no such line, or when this host is the named coordinator, it does nothing. Otherwise each pass runs `ssh -o BatchMode=yes -o ConnectTimeout=6 <name> true` with a ten second limit; a failed fetch alone does not count as the coordinator being offline. After `offline_minutes` of ssh failures it sends one alert, `coordinator <name> offline for <n> minutes; failover is manual, ask the owner`, by running `alert_command` with the text as its last argument (the private config picks the channel) and adding it to the normal notices even when `alert_command` fails, so configured runs and the log still see the line; a failed `alert_command` leaves `alerted` false and is retried on the next pass. When the coordinator answers again the state clears and one `coordinator <name> back` line goes out if an alert had been sent. A changed coordinator name resets the timer. This check runs first, before any Orca call, and saves its state at once. With no coordinator Run it skips every Orca call, so a host without Orca passes cleanly. It only alerts: it starts nothing and fails over nothing.
